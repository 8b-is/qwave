# Xcode Cloud

Qwave can build and test on **Xcode Cloud** (Apple's cloud CI/CD, built into
Xcode + App Store Connect). This document covers what is wired in the repo and
the one-time setup that has to be done in Xcode / App Store Connect with the
team's Apple Developer enrollment.

## What lives in the repo

`ci_scripts/ci_post_clone.sh` — the only repo-side piece Xcode Cloud needs.
It runs after Xcode Cloud clones the repo and, because:

- `Qwave.xcodeproj` is **generated by XcodeGen and gitignored** (there is no
  project in a fresh clone), and
- PacketTunnel links a **Zig** static lib and a **Go** (WireGuard) bridge,

it `brew install`s `xcodegen zig go` and runs `xcodegen generate --spec
project.yml`. This mirrors `.github/workflows/ci.yml`. Without it, an Xcode Cloud
build fails immediately ("no project/workspace" or a missing `zig`/`go`).

The build scheme (`Qwave`) is already shared (`xcodegen` emits it into
`Qwave.xcodeproj/xcshareddata/xcschemes/`), which Xcode Cloud requires.

## Recommended scope: Build + Test only

Qwave is distributed **outside the Mac App Store** — Developer ID signing +
notarization + Sparkle + GitHub Releases, driven by `.github/workflows/release.yml`.
That release pipeline should stay as-is. Xcode Cloud's Archive/Distribute path is
built around App Store / TestFlight signing and does **not** fit Qwave's manual
Developer-ID + provisioning-profile model.

So use Xcode Cloud for **Build + Test** (fast health checks, parallel testing,
Apple-integrated results), and keep GitHub Actions for release/distribution. Do
not add an Archive action unless Qwave adopts Mac App Store / TestFlight.

## One-time setup (Xcode / App Store Connect — needs the Apple ID)

These steps require signing in with the Apple Developer team (`7CFQYBX575`) and
accepting the Xcode Cloud terms; they cannot be scripted from the repo.

1. **App Store Connect record.** Ensure an app record exists for bundle id
   `is.8b.qwave` (App Store Connect ▸ Apps ▸ +). Required even for a non-App-Store
   app so Xcode Cloud has a product to attach the workflow to.
2. **Create the workflow.** In Xcode: **Integrate ▸ Create Workflow** (or the
   Report navigator ▸ Cloud). Pick the `Qwave` product, grant Xcode Cloud access
   to the GitHub repo `8b-is/qwave`, and accept the Xcode Cloud terms.
3. **Environment.** Pin **Xcode 26.3** and a recent **macOS** image to match CI
   (`.github/workflows/ci.yml` asserts Xcode 26.3).
4. **Start conditions.** Recommended: *Pull Request* changes targeting `main`
   (and optionally *Branch* pushes to `main`).
5. **Actions.**
   - **Build** — scheme `Qwave`, configuration `Release`. Add
     `CODE_SIGNING_ALLOWED=NO` (custom build setting / env) so the health-check
     build does not require signing, matching CI.
   - **Test** — the unit tests live in the `QwaveKit` Swift package
     (`swift test -c release --package-path Packages/QwaveKit`). The `Qwave`
     scheme's test action must include the `QwaveKit` package tests (add them to
     the scheme's Test targets, or use a test plan) for Xcode Cloud's Test action
     to run them; otherwise keep Test off and rely on the GitHub Actions
     `swift test` lane.
6. **Save & run.** The first run executes `ci_post_clone.sh`; watch its log to
   confirm `xcodegen generate` and the toolchain installs succeed.

## Notes

- `ci_post_clone.sh` runs with its working directory set to `ci_scripts/`; it
  `cd`s to `$CI_PRIMARY_REPOSITORY_PATH` before generating the project.
- If a Homebrew formula install is ever flaky in the Xcode Cloud image, that is
  the first place to look — the script sets `HOMEBREW_NO_AUTO_UPDATE=1` to keep
  installs fast and deterministic.
- Reference: Apple, "Writing custom build scripts" and "Running custom scripts
  during a build."
