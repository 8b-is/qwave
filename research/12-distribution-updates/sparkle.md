## What it is

The software update framework for macOS. Sparkle 2 supports application sandboxing, custom user
interfaces, updating external bundles, and a modernised installer architecture with faster and
more reliable installs.

Updates are described by an **appcast** — an RSS feed of available versions — and every update is
verified with an **EdDSA signature** before installation. That signature is the security model:
even a compromised download host cannot serve a malicious update without the private key.

The 2.9.5 security fix is worth reading as a signal: hardening delta patching against a symbolic
link at the destination path is the kind of vulnerability class an update framework must get
right, and finding and fixing it is evidence of active security maintenance.

## Why it matters for Qwave

It closes the gap between "Qwave ships security features" and "Qwave can ship security fixes".

Today, a vulnerability in `Shields`, `VPNKit`, or `Persistence` reaches users only when they
happen to visit GitHub Releases and manually download a new zip. For a browser, that is the
single largest weakness in the product.

### External bundle updates matter here specifically

Sparkle 2 supports updating **external bundles**, which is directly relevant: Qwave ships
`PacketTunnel.systemextension` alongside the app. Updating a system extension has its own rules
around approval and versioning, and a framework that understands multi-bundle updates is the
right foundation.

### The appcast signature fits the threat model

A sovereign browser's users are exactly the people who should ask "how do I know this update is
really from you?" EdDSA-signed appcasts give a real answer, and the answer is verifiable
independently of GitHub, TLS, or the CDN.

## The prerequisite: signing

Sparkle cannot be adopted before code signing. The chain:

| Step | Status | Blocks |
|------|--------|--------|
| Developer ID certificate | Missing | Everything below |
| Signing app + system extension | Missing | Notarisation, VPN approval |
| Notarisation + stapling | Missing | Gatekeeper-clean launch |
| Sparkle EdDSA appcast | Missing | Auto-update |

`docs/SIGNING.md` exists, which suggests this is understood and planned. Worth restating: **the
VPN feature cannot fully work for end users until signing is done**, because network extensions
require proper entitlements and a signed, notarised host app. Signing unblocks both auto-update
and Stage B of the VPN — it is the highest-leverage non-code work available.

## Apple Silicon notes

Native and universal-binary aware. One deployment note: if Qwave ever ships architecture-specific
builds, the appcast supports per-architecture entries. Since Qwave is Apple Silicon-only, a
single arm64 build is correct and simpler.

## Adoption sketch

```swift
// project.yml — app target dependency
packages:
  Sparkle:
    url: https://github.com/sparkle-project/Sparkle
    from: 2.9.5
```

```swift
// QwaveApp/AppDelegate.swift
import Sparkle

private let updaterController = SPUStandardUpdaterController(
    startingUpdater: true,
    updaterDelegate: nil,
    userDriverDelegate: nil
)
```

`Info.plist` (generated by XcodeGen from `project.yml` — never hand-edited):

```
SUFeedURL              https://qwave.8b.is/appcast.xml
SUPublicEDKey          <base64 EdDSA public key>
SUEnableAutomaticChecks true
```

Signing the appcast in `release.yml`:

```bash
./bin/sign_update Qwave-v0.2.0.zip    # private key from a CI secret, never committed
```

Add a **Check for Updates…** item to `MainMenu.swift`, and a preferences toggle in the Settings
window. For a sovereignty-focused product, automatic update checking should be a visible,
user-controlled setting — and worth being explicit that the check itself is a network request,
so users who want zero background traffic can turn it off.

## Risks

- **The EdDSA private key is critical infrastructure.** Whoever holds it can ship code to every
  user. Store it in a CI secret with tight access, never in the repository, and have a documented
  key-rotation plan before the first release.
- **Update checks are network traffic.** A privacy-focused browser phoning home on a schedule
  needs to be disclosed and controllable. Make the setting visible and honour it.
- **System extension updates are subtle.** Updating an app that hosts an approved system extension
  can require re-approval. Test the full flow on a clean machine, not just an upgrade path.
- **Signing must come first.** Sparkle installing an unsigned update is worse than no updater —
  it is an unauthenticated code-execution path.
- **Appcast hosting.** The feed must be served over HTTPS from infrastructure you control. The
  EdDSA signature protects integrity even if the host is compromised, which is the point of it.

## Verdict

🟢 **Adopt — after code signing, which is the real blocker.**

Sparkle is the standard for non-App-Store Mac distribution, actively maintained, security-focused,
and it fits Qwave's needs including the system extension case.

**The finding that matters is not about Sparkle.** It is that unsigned distribution is currently
the weakest part of a product whose entire premise is security and sovereignty — and that the
same fix unblocks the VPN feature described in the README. Getting a Developer ID certificate and
wiring signing and notarisation into `release.yml` is the highest-leverage work identified
anywhere in this research folder.

Sparkle is what you add once that is done.
